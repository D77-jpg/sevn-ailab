开题答辩上，AI 方向的同学最常被问住的一句话是：**「你的创新点在哪？」**

最常见的回答是：「本系统采用了大模型技术，实现了智能化的 XX。」

这不是创新点。这是**技术选型**。导师听到这句话，脑子里想的是：调一个 API 谁都会，你自己做了什么？

## 为什么 AI 题更容易被追问

传统的管理系统题，工作量是看得见的：几张表、几个模块、多少接口。

AI 题恰恰相反。**一个下午就能调出一个能跑的 demo**，导师分不清哪些是模型的功劳，哪些是你的。所以他会追问，而且会追问得比别的题更狠。

好消息是，这也意味着你只要把「你的那部分」讲清楚，就比大多数同学强。

## 一个判断标准：三件套

一个站得住的创新点，必须同时有三样东西：

**1. 一个具体的问题。** 不是「提升智能化水平」，而是「模型在报价时会低于底价」。

**2. 一个你做的处理。** 不是「采用大模型」，而是「把底价校验从模型手里拿走，交给代码」。

**3. 一个能量出来的结果。** 不是「效果显著提升」，而是「在 80 条测试询盘上，违规报价从 X 条降到 0 条」。

缺第一样，是空话；缺第二样，是在夸模型；缺第三样，答辩时一定会被问「你怎么证明」。

## 三种本科能做完、答辩讲得清的写法

### 写法一：确定性拆分

**核心句式：** 「针对 XX 环节模型输出不稳定的问题，本文将其中可规则化的判断从模型中剥离，由程序校验。」

这是我最推荐的写法，因为它几乎适用于所有大模型应用题，而且工作量真实可见。

做法是把你的业务流程画出来，逐个环节问一句：**这个判断有确定答案吗？** 有，就写成代码；没有，才交给模型。

举例：在一个询盘处理系统里，「这条询盘问的是哪个产品」需要理解语言，交给模型；「报价是否低于底价」「库存够不够」有确定答案，交给代码。模型提出方案，代码校验，不通过就打回重来。

**可测的指标：** 错误输出的数量或比例，拆分前 vs 拆分后。我自己做外贸数字员工时，这一步把误报率从 12% 压到了 0——这种前后对比，就是答辩现场最有说服力的一页 PPT。选题库里的[外贸询盘处理系统](/topics/tool-calling-inquiry/)就是按这个思路收窄的。

### 写法二：面向领域数据的检索策略

**核心句式：** 「针对 XX 类文档结构特点，本文设计了 XX 切分与召回策略，相比通用固定长度切分，命中率提升 X%。」

适合 RAG 知识库问答类题目，比如选题库里的[校园规章问答系统](/topics/rag-policy-qa/)。通用教程都是「按 500 字切一块」，但你的数据往往有结构：规章按条款、教材按章节、客服记录按问答对。

**按你数据的结构来切**，本身就是一个合理的、你自己的设计决定。

**可测的指标：** 准备 50–100 个问题，人工标出每个问题的正确出处，比较两种切分方式下正确段落有没有被召回（Top-3 命中率就够用）。

### 写法三：人在回路的可控性设计

**核心句式：** 「针对 Agent 执行不可逆操作的风险，本文设计了基于操作分级的人工确认机制。」

适合 Agent、Tool Calling 类题目，比如[基于 MCP 的校园事务助手](/topics/mcp-campus-assistant/)。发邮件、改数据、下订单，这些动作一旦做错就收不回来。

做法是给系统里的每个工具标一个等级：只读的直接执行，可逆的记录日志，不可逆的必须中断、等人确认。

**可测的指标：** 在一组测试任务里，未经确认执行的高风险操作次数（目标是 0），以及需要人工介入的比例（越低说明分级越准）。

## 三种不要写的「创新点」

**「首次将大模型应用于 XX 领域」。** 你查不到，不代表没人做过。导师随手一搜就能找到反例，这是最容易翻车的一句。

**「显著提高了效率 / 准确率」，但没有数字。** 没有基线、没有测试集的「提高」，答辩时等于没说。

**「采用了最新的 XX 模型」。** 模型是别人训练的。换模型是配置，不是创新。

## 开题时还没结果，怎么写？

开题阶段系统还没做完，你当然拿不出数字。但你可以、也应该写清楚**打算怎么验证**：

- **基线是什么**：和什么比？（直接让模型做 / 通用切分 / 无确认机制）
- **指标是什么**：量什么？（错误数、命中率、介入比例）
- **测试集从哪来**：多少条、怎么构造、谁来标注？

把这三行写进开题报告的「研究方法」或「预期成果」里。导师看到这个，就知道你不是在凑字数，而是真的知道自己要证明什么。

而且，**测试集本身就是你工作量最硬的证据**。一份自己整理、自己标注的 80 条数据，比十页技术背景介绍更能说明你做了事。

## 一个改写示范

改写前：

> 本系统基于大语言模型，实现了智能客服功能，具有较高的实用价值和创新性。

改写后：

> 针对大模型在回答售后政策类问题时容易编造条款的问题，本文按政策条款结构对知识库进行切分，并要求模型回答时必须引用条款编号，由程序校验编号是否真实存在。计划在 60 个售后问题构成的测试集上，对比通用切分方式下的条款命中率与编造回答数量。

后者长了一倍，但每一句都经得起追问。

## 开题前的自查清单

- [ ] 我的创新点能用一句话说出「什么问题 + 我怎么处理」吗？
- [ ] 去掉「大模型」三个字，这句话还有内容吗？
- [ ] 我写清楚了基线、指标和测试集吗？
- [ ] 如果导师问「为什么不直接让模型做」，我有答案吗？
- [ ] 这个设计是我自己想明白的，我能在白板上把它画出来吗？

最后一条最重要。创新点写得再漂亮，答辩时也是你一个人站在台上讲。**能讲清楚的，才是你的。**
